# ドキュメント

## 細かい仕様
README.mdに書かれていない細かい仕様をここに記す。

改行コードはCRLFまたはLFのみを許容する。CRのみはサポートしない

識別子はトランスパイル後も維持される。

コメントはトランスパイル後も維持される。ただしプロンプト内のコメントは例外的に取り除かれる。

Coraft側のプリプロセッサ命令やマクロは処理、展開されてからC++になる。


C++の予約語（`__`から始まる識別子や先頭が`_`で直後に大文字英字が入る識別子を含む。これらは処理系依存の予約語である）であり、Coraftの識別子ではない記号がユーザー識別子として定義、もしくは使用された場合、その識別子の先頭に`co_`を付け加えてマングリングする。識別子をマングリングした形と衝突する変数名(`co_not`)をユーザーが定義した場合、それもマングリングする(`co_co_not`のようになる)。この処理は再帰的に行われる。`main`関数は厳密には予約語ではないが、これにも同様の処理を行う。`main`をマングルした場合、ラッパーが自動的に挿入される。

定義に`export`キーワードをつけるとコンパイル時にヘッダーに宣言/定義が切り出される。
ヘッダ内の定義(ジェネリクス関数の定義内など)でexportではない定義への依存があった場合、その依存先を`internal`名前空間に入れる。
Coraftコード内で`internal`、`detail`、`impl`という名称の名前空間を定義・使用しようとすると、C++コード上ではマングリング(`co_internal`、`co_detail`、`co_impl`)される。この三語のうち`detail`は単に内部実装以外にも使うケースがあり得るので、そのような場合においての衝突回避のための仕様である。マングリングした形と衝突する名前空間名が定義された場合、それにもマングリングを行う(`co_co_internal`、`co_co_detail`、`co_co_impl`)。この処理は再帰的に行われる。

トランスパイル後も残るコメントとそうでないコメントが存在する。例えば文の途中のコメントはトランスパイル後には消える。

`;`は空のブロックを表し、文は必ずブロックで終了する。

トランスパイル後もコメントが残る位置は以下である。
- グローバル
- ブロック直下
- 列挙型の値定義の前後 (下記「コード1」は残る)
- 名前空間スコープの直下
- ブロックの前後
- 名前空間スコープの前後

コード1
```Coraft
enum Sample{
	A,
//コメント B, //コメント
	C,
}
```


プラットフォーム毎に事前定義のマクロが存在する。（例：Windows → WINDOWS, Linux → LINUX, MacOS → MACOS）
生成されるコードは特定の一プラットフォームのみに向けたものである。

要するに
```Coraft
@if(WINDOWS)
{
	hoge();
}
@else
{
	huga();
}
```
は、Windows向けには
```c++
	hoge();
```
にトランスパイルされる。
